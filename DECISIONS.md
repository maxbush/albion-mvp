## D1. Единственный интерфейс — Telegram

**Контекст.** Пользователи системы — родители, репетиторы, координаторы.
**Решение.** Весь UI живёт в Telegram: команды, inline-кнопки, свободный
текст. Никаких веб-панелей, личных кабинетов, приложений.
**Почему.** Установка = ноль, обучение = ноль, доставка уведомлений
гарантирована тем же каналом, которым пользуются все стороны. Любая панель
администрирования — это второй продукт, который надо строить и защищать.
**Отказались от:** веб-дашборда (вернёмся при масштабе 100+ занятий/день —
там появится потребность в массовых операциях).
**Статус.** ✅ Ядро продукта. Следствие: E2E-качество проверяется харнессом
эмуляции Telegram-апдейтов, а не браузерными тестами.

## D2. Management by Exception — человек только по исключению

**Контекст.** Координатор репетиторской компании тонет в рутине: обзвоны,
напоминания, контроль «а начался ли урок».
**Решение.** Система сама ведёт каждый сценарий (напомнить → спросить →
подождать → закрыть). Координатор получает сообщение **только** когда
автоматика исчерпала себя: родитель молчит, репетитор не подтвердил старт,
урок не перешёл в live.
**Почему.** Экономия — не «минуты на сообщение», а целая роль. Ценность
доказывается демо-сценарием неявки за 15 минут.
**Отказались от:** потоковой ленты всех событий для координатора (шум
убивает внимание; исключения тонут).
**Статус.** ✅ Главная продуктовая идея, зафиксирована в OWNER_GUIDE §2.

## D3. Событийная шина (in-memory pub/sub) + Workflow Engine поверх SQLite

**Контекст.** Сценарии длинные во времени (напомнить за 15 минут,
эскалировать через 15 минут молчания), процесс может перезапускаться.
**Решение.** События — через простой in-memory EventBus; отложенные
действия — записи `scheduled_actions` в SQLite; состояние сценариев —
таблица `workflow_instances`. Шедулер тикает по БД, переживает рестарт.
**Почему.** Для MVP Postgres/Kafka/Celery — операционный долг без выигрыша;
SQLite в WAL-режиме надёжен и не требует администрирования. Правильные
вещи сделаны сразу: lock'и задач, 3 повтора, DLQ, уведомление координатора
при провале, сбор «зомби»-задач, поле идемпотентности.
**Отказались от:** apscheduler (удалён в R7-12 — дублировал наш цикл),
RabbitMQ/Temporal (преждевременно).
**Статус.** ✅ Масштабный предел — десятки классов/день. Дальше — Postgres
(миграция изолирована в слое repository).

## D4. MeritHub = «import & observe» (create-only вендор)

**Контекст.** Внешняя система расписания — MeritHub. Выяснено опытным путём:
у вендора **нет методов чтения и отмены** занятий — только создание
классов/пользователей и push-webhook'и о событиях.
**Решение.** Мы создаём классы/пользователей через API, дальше живём по
webhook'ам (`classStatus`: `lv`=урок идёт, `cp`=завершён, `cl`/`ex`/`up` —
закрыт/истёк/предстоит; `attendance` — кто пришёл). Источник правды о
расписании — **наша локальная БД** (merithub_classes, enrollments,
contacts). Mock-провайдер имеет те же методы, что и реальный клиент
(R7-10: фейковые «чтение/отмена» из мока убраны — они лгали о возможностях
вендора).
**Почему.** Нельзя строить логику на API, которого нет; лучше честная
модель «создали → наблюдаем», чем сюрпризы в проде.
**Отказались от:** попыток эмулировать get/cancel «на всякий случай».
**Статус.** ✅ Подтверждено R7-аудитом. Следствие — D8 (локальные серии).

## D5. Vendor-agnostic интеграции (фабрика + mock-first)

**Контекст.** На старте нет ключей MeritHub, а демо нужно завтра.
**Решение.** `src/integrations/factory.py` возвращает mock или реальный
клиент по наличию ключей в `.env` (`MERITHUB_CLIENT_ID/SECRET` → реальный;
иначе mock). Логика воркфлоу не знает разницы.
**Почему.** Пилот продаётся без доступа к боевому MeritHub; переход в бой —
две строки в `.env`, а не релиз.
**Отказались от:** жёсткой привязки к MeritHub в бизнес-логике.
**Статус.** ✅ Паритет mock/real проверяется контракт-тестом.

## D6. Каноническая зона расписания организации

**Контекст.** Ученики и репетиторы разбросаны по поясам (Лондон, Алматы…),
а «среда 15:00» должна означать одно и то же для всех.
**Решение.** Одна настройка `ALBION_ORG_TIMEZONE` (по умолчанию
`Europe/London`): все занятия создаются и хранятся в ней; невалидное
значение деградирует в Europe/London с warning'ом. Зоны участников — поле
профиля, используется **только** для отображения («15:00 London [+4ч]»).
**Почему.** Двусмысленность времени — источник №1 срывов уроков; единая
точка правды исключает класс багов «кто в какой зоне создал».
**Отказались от:** хранения времени в зоне каждого участника (несколько
«правд» = гонки при DST).
**Статус.** ✅ H4/P4.1, подтверждено владельцем. Все карточки координатора
показывают время в org-зоне (R7-4).

## D7. Регулярные занятия — паттерн дней (occurrence-aware), а не 52 строки

**Контекст.** Perma-серия «каждую ср/пт» — это бесконечное расписание.
**Решение.** В БД хранится паттерн (`schedule_days: ["WE","FR"]`), каждый
показ («что сегодня», «ближайшие 7 дней») материализует ближайшие
вхождения функцией `class_occurs_on/class_occurs_between`.
Таблица материализованных вхождений (`merithub_occurrences`) спроектирована,
но сознательно НЕ включена — владелец отложил (H2, 2026-08-01).
**Почему.** Паттерн не рассинхронизируется с собственными копиями;
«перенести одно занятие серии» — осознанно следующий этап (тогда и
включим материализацию per-date).
**Отказались от:** генерации строк на год вперёд (классический источник
рассинхрона при правках серии).
**Статус.** ✅ Работает; переносы отдельных дат — в роадмапе.

## D8. AI-слой: дешёвая модель — рабочая лошадка, эвристика — фолбэк

**Контекст.** Нужно понимать свободный текст («сын не придёт», «running
late, wifi dying»), но ключ OpenRouter есть не всегда.
**Решение.** Все вызовы идут через `llm_cheap_model`; «умная» `llm_model`
зарезервирована под сложные сценарии. Без ключа — детерминированные
эвристики по RU/EN словарям; mock LLM сканирует текст пользователя, а не
шаблон промпта (баг, найденный только аудитом R7-9: шаблон сам содержал
слова-триггеры).
**Почему.** Пилот должен работать в любом окружении, а поведение в mock —
предсказуемым и честным.
**Отказались от:** гонки за самой сильной моделью для intent-классификации
(дорого и не нужно).
**Статус.** ✅ i18n RU/EN в паритете (30 ключей, тест паритета).

## D9. Честный UX: никаких «Обрабатываю…» в пустоту

**Контекст.** Аудит R7 нашёл класс дефектов «фантом»: бот подтверждал
действия, которые нигде не выполнялись; техстроки (`UTC`, сырое `C9`,
`Actor:`) торчали в карточках координатора.
**Решение.** Правило: каждое намерение пользователя получает честный ответ
(включая «не понял — передаю координатору» с кнопкой связи); все времена —
в org-зоне словами; все ID — с человеческими подписями; отправитель всегда
получает ack.
**Почему.** Доверие к боту решает, будут ли ему писать родители. Одна
ложная «обработка» — и канал мёртв.
**Статус.** ✅ R7-1…R7-5, P1-tail. Покрыто тестами на тексты.

## D10. Идемпотентность: nonce на кнопках, флаг-после-публикации

**Контекст.** Планировщик может выполнить действие повторно (requeue после
ошибки); родитель может нажать кнопку дважды/со старого сообщения.
**Решение.** Callback кнопок содержит одноразовый nonce из данных workflow —
старые кнопки отвергаются. Действия-эффекты помечаются флагами в данных
воркфлоу (`notify_parent_sent`) — повторный тик выходит молча. Флаг
ставится ПОСЛЕ публикации события: редкий дубль сообщения при падении в
окне осознанно предпочтительнее потери уведомления.
**Почему.** «Не спамить и не терять» — два края, компромисс выбран в
пользу доставки.
**Статус.** ✅ R7-16 + пилотные решения R3. E2E: тройной тик = 1 сообщение.

## D11. Оплаты выключены (до Xero)

**Контекст.** Учёт оплат/баланса — хотели сразу.
**Решение.** Владельцем (Round 3) платёжные события выключены; типы
`PAYMENT_*` удалены из кода (R7-13), чтобы не висеть фантомами. Возвращаем
вместе с интеграцией Xero.
**Почему.** Недоделанная фича в коде хуже, чем никакой: она ломает
доверие к метрикам и тестам.
**Статус.** ⏸ Ждёт решения по Xero (роадмап, этап 3).

## D12. Роли для пилота — самоназначаемые (аппрув отложен)

**Контекст.** Любой может взять роль coordinator и видеть эскалации с
персональными данными.

**Статус.** ⏸ Осознанный риск пилота (H1 в MASTER_PLAN).

## D13. Мёртвое удаляется, а не комментируется

**Контекст.** За 7 раундов накопились: таблица `conversations` (0 ссылок),

**Почему.** Мёртвый код — это ложная карта для следующего разработчика.
**Статус.** ✅ R7-10…R7-14. Гигиена закреплена правилом плана.

## D14. Kill Switch вместо «аккуратного деплоя»

**Контекст.** Живая система шлёт реальным людям; ошибка в новом релизе =
спам клиентам.
**Решение.** `/kill_switch`: 🔴 всё выкл / 🟡 только координаторам /
🟢 штатно. Деплой: 🟡 → наблюдаем → 🟢.
**Почему.** Возможность мгновенно «стушеваться» дешевле идеальных релизов.
**Статус.** ✅ Уровень виден в `/status`.

## Д15. Доступ к опасным командам выровнен, tech-разделы — владельцу

**Контекст.** Аудит нашёл, что опасные демо-рассылки и техсекции `/status`
проверяли доступ кто как.
**Решение.** Демо-функционал жёстко за `ALBION_DEMO_MODE`; опасные команды —
по ролям согласованно; техданные (интерьеры шины, модели) видны владельцу.
**Почему.** Поверхность атаки у пилота маленькая, но порядок должен быть
одинаковым везде.
**Статус.** ✅ Решения раунда 5-6, подтверждено R7.

## Приложение. Ограничения MeritHub (собраны опытом, обновлено R7)

1. **Create-only API:** создать класс/пользователя/зачисление можно;
   прочитать занятие или отменить его через API — нельзя. Модель работы —
   «создали → наблюдаем за webhook'ами».
2. **Webhook'и не подписаны.** Приёмник принимает payload как есть
   (опциональный секрет включается одной настройкой
   `MERITHUB_WEBHOOK_SECRET`, когда вендор начнёт подписывать).
3. **`classStatus` — коды:** `lv`=идёт, `cp`=завершён, `cl`=закрыт,
   `ex`=истёк, `up`=предстоит; идентификация — `classId` (+`subClassId`
   у серий; маппинг sub→parent — отложенная задача H2).
4. **Неявку в реальном времени MeritHub не сообщает.** Закрываем тремя
   каналами: attendance-webhook после урока, кнопка «ученик не пришёл» у
   репетитора при старте, контроль перехода урока в `lv` через 5 минут.
5. **OAuth2 + JWT-грант** (`urn:ietf:params:oauth:grant-type:jwt-bearer`),
   три хоста (service/class/live), таймаут 15с; отладка тел запросов —
   `MERITHUB_LOG_PAYLOAD=true`.

## Приложение. Дорожная карта (владелец, 2026-08-01)

1. **Отложено осознанно (решения владельца):** аппрув роли coordinator
   (H1 — отложен для тестирования), `merithub_occurrences` (H2 — при
   переносах), EN-тексты носителем (H3), WhatsApp-мост (H4 — ограничения
   Business API изучены: 3 quick-reply, 24-часовое окно, помеседжная
   оплата), docker-volume БД (H5).
2. **Этап 2:** переносы отдельных занятий серии (включает D7-материализацию),
   подтверждение занятий, авто-сборка недели.
3. **Этап 3:** оплаты/баланс по Xero (включает D11), напоминания об оплате.
4. **Этап 4:** авто-онбординг лидов (уже есть захват + `/leads`), аналитика
   по событиям `LESSON_STARTED/COMPLETED` (метрики появились в R7-13).

Платформа для всех этапов одна: события → workflow → Telegram → эскалация
по исключению.
